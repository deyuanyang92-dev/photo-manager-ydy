# 当前需求与产品行为基线

更新日期：2026-07-12
适用版本：v0.59

本文是 GitHub 上的当前需求入口。发生冲突时，优先级依次为：用户最新明确要求、本文、`PROJECT_MEMORY.md`、当前 `specs/`；`audit/`、历史计划和复盘只用于追溯。

## 1. 工作台与合成

- 用户手选 JPG 后，`合成` 与 `合成+整理` 不要求先激活编号。
- 有激活编号时，结果归入该编号并自动使用下一成果序号。
- 无激活编号时，必须让用户选择目标编号或自由输出名；不得静默生成含糊文件名。
- 没有手选 JPG 时，只有用户明确开启自动归档，才可按激活编号自动选择照片。
- 完成状态只能在后台任务真实结束、文件与数据库提交成功后显示。

## 2. 文件生命周期

- TIFF 是无损母版，任何自动流程都不得删除；仅允许用户明确确认后的手动删除或撤销操作。
- 默认归档为可直接解压的普通 JPG ZIP。高压缩 JPEG XL 是可选模式。
- 归档先写同目录临时文件，校验完成后原子替换最终 ZIP；取消或失败保留原有同名 ZIP。
- 散落 JPG 只在 ZIP 完整性、文件大小和 SHA-256 全部通过后清理。
- 数据库提交与磁盘操作必须保持一致；失败要可见，不能静默假装成功。

## 3. ZIP 还原

- 成果区支持单选和多选 ZIP 还原原片。
- 已关联分组：JPG 恢复到记录的原路径，TIFF 保留；成功后项目内 ZIP 直接删除，分组退回“已合成、待整理”。
- 不创建 `_retired-zip` 或其他永久 ZIP 备份。
- 孤儿/外部 ZIP：恢复 JPG 副本，原 ZIP 保留。
- 恢复出 0 张、校验失败、数据库保存失败或 ZIP 删除失败时，不得清除归档登记；失败项可重试。
- ZIP 成员路径必须限制在临时目录/目标目录内；覆盖目标时先在同目录暂存并校验，再原子替换。

## 4. 批量与并行

- 列表、表格、成果卡片等具备同类操作的区域，应支持标准多选、全选/取消选择和批量操作。
- 批量还原、批量归档、分类批量更新等耗时文件任务，在目标互不冲突时并行执行。
- 同一路径冲突、数据库写入和最终状态提交保持顺序执行，避免竞态。
- 批量任务必须逐项隔离失败，汇总成功、跳过和失败数量；一个失败不能误删其他项。
- 并发数使用设置值并限制合理上限；界面线程不得执行重型压缩、解压或哈希计算。

## 5. 字体与界面一致性

- 弹窗、任务进度、按钮、说明文字使用统一字体层级，正文不应明显大于主界面正文。
- 设置页提供全局字体缩放，保存后持久化，并作用于主界面与软件自有弹窗。
- 默认字号保证信息密度和可读性；用户缩放不应破坏布局、截断关键按钮或让任务状态不可见。
- 能在当前页面完成的操作优先使用内嵌区域，避免不必要的模态弹窗。

## 6. 分类、名录与汇总

- `名录` 表示物种/分类名录，不是照片处理进度表。
- 未鉴定材料和仅工作流状态的记录不进入物种名录，应进入样品处理汇总。
- 混合管或同一批多个物种允许追加鉴定，并持久保存额外分类信息。
- 勾选与行选择同时存在时，批量更新和导出使用两者并集。
- 数据汇总保存真实 TIF 路径；“TIF 转 JPG 导出”是派生导出，不改变母版登记。

## 7. 协作

- “团队永久码”和“项目共享码”是两个独立流程，不能用其中一个冒充另一个已完成。
- 协作完成度以用户可见且可操作的界面状态为准；只有后端接口存在不算功能完成。
- 网络发现、离线队列和数据库写入失败必须显示真实状态并允许恢复。

## 8. 验证与发布

- 代码修改前检查 Git 状态并保留用户无关改动。
- 先运行 `python -m compileall -q app main.py`，再运行受影响模块测试和核心回归。
- UI 改动完成后启动软件进行可见检查。
- `APP_VERSION`、README、安装文档和 Git 标签必须一致；标签触发 Windows 发布构建。
- 不承诺“绝对无 bug”；发布结论应明确已验证范围与剩余风险。
